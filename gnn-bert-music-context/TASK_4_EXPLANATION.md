# Task 4: MusicCaps Audio-Text Retrieval

## 1. What Task 4 does

Task 4 tests whether the system can match a natural-language music description with the correct audio clip.

The system receives paired examples:

```text
(audio clip, caption describing that clip)
```

It learns to place matching audio and captions close together in a shared embedding space. After training, a caption can be used to retrieve the audio clips that the model thinks best match it.

This is a retrieval task, not an audio-generation task and not a caption-writing task.

## 2. What the `caption` field contains

The captions come from the official MusicCaps metadata file:

```text
data/raw/musiccaps/musiccaps-public.csv
```

Each caption is a natural-language description of the corresponding MusicCaps audio/video clip. It can describe things such as:

- instruments and musical texture
- vocals, vocal style, or whether the clip is instrumental
- rhythm, melody, harmony, and production characteristics
- mood or emotional quality, such as happy, emotional, ominous, calm, or energetic
- sound effects that can be heard in the clip
- the possible context of the source recording, such as a live performance, tutorial video, game-like music, or background music

For example, a caption may say that a clip contains an electric guitar, drums, piano chords, crowd sounds, and an emotional male vocal. Another caption may describe an opera-style female vocal with violins and bass.

The caption is therefore a human-written semantic description of what can be heard and sometimes the context in which the audio appears. It is not necessarily:

- a transcript of lyrics
- a transcript of the video speech
- the title of the video
- a list of ground-truth genre labels
- a description generated by our project

Some captions mention the surrounding video context because the source clip may contain music used in a tutorial, game, movie, live performance, or other setting. The model still uses the complete caption as text input.

## 3. How captions enter our project

The pipeline is:

```text
Official MusicCaps CSV
        |
        | read ytid, start_s, end_s, caption
        v
Download the timestamped audio section
        |
        v
Build an audio graph from the local WAV clip
        |
        v
Create a manifest containing the graph and the same caption
        |
        v
Train and evaluate the audio-text retrieval model
```

`src/download_musiccaps.py` reads the YouTube ID and timestamps from the CSV and downloads only the requested audio section.

`src/preprocess_musiccaps.py` processes the local audio into graph features and writes records containing fields such as:

```json
{
  "track_id": "musiccaps_id",
  "audio_path": "...wav",
  "graph_path": "...pt",
  "caption": "the original MusicCaps description",
  "text_context": "the same caption",
  "caption_start_s": 0.0,
  "caption_end_s": 10.0
}
```

The important alignment rule is that the audio and caption must come from the same verified MusicCaps ID. If the local audio file is unavailable, the record is skipped. We do not invent an audio-caption pair.

## 4. How the model works

### Audio side

1. The downloaded clip is converted to a local WAV file.
2. The audio is divided into segments.
3. Mel, chroma, and MFCC-related features are extracted.
4. Each segment becomes a node in a PyTorch Geometric graph.
5. Temporal and similarity edges connect related segments.
6. The GNN produces one graph-level audio embedding.

### Caption side

1. The original MusicCaps caption is tokenized.
2. DistilBERT converts the caption into contextual text representations.
3. The text representation is projected into the same embedding size as the audio representation.
4. The model produces one caption embedding.

### Shared embedding and similarity

The audio and caption embeddings are normalized and compared with cosine similarity:

```text
similarity(audio, caption) = normalized_audio dot normalized_caption
```

During training, the correct audio-caption pair is treated as the positive pair. Other items in the same batch act as negative examples. The InfoNCE loss teaches the model to give higher similarity to the correct pair than to mismatched pairs.

The code uses a symmetric loss, so it learns both directions:

- caption to audio
- audio to caption

## 5. What the automatic retrieval result means

For each test caption, the system calculates similarity against the test audio clips and sorts the clips from highest to lowest similarity.

The top three results are exported to:

```text
results/retrieval_examples/musiccaps_examples.json
```

The automatic evaluation reports:

- Caption-to-audio Recall@1: the correct audio is ranked first
- Caption-to-audio Recall@5: the correct audio is within the first five
- Caption-to-audio Recall@10: the correct audio is within the first ten
- Audio-to-caption versions of the same metrics

These metrics measure retrieval performance using the known paired IDs. They do not prove that every top-ranked clip is semantically convincing to a human, especially on a small test set. That is why human evaluation is needed.

## 6. Why human evaluation is needed

The model's similarity score is an automatic numerical judgment. It may rank a clip highly because it detects broad similarities such as:

- similar instruments
- similar mood
- similar vocal style
- similar rhythm or production

However, a high score does not guarantee that a person agrees that the retrieved clip matches the full caption. Human listeners provide an independent quality check.

Human evaluation answers a different question:

> Does this retrieved audio actually match the information and overall description in the caption when a person listens to it?

This is required because Task 4 includes qualitative retrieval evaluation and the assignment asks for ratings from at least five listeners.

The human rating is **not** the model similarity score. It must not be calculated from the similarity value. A listener should read the caption, listen to the retrieved audio, and then independently give a score from 1 to 5:

| Rating | Meaning |
|---|---|
| 1 | Does not match the caption |
| 2 | Weak match |
| 3 | Partial match |
| 4 | Good match |
| 5 | Very strong match |

## 7. Our five-person CSV workflow

We are using the CSV directly, not a Google Form.

The evaluation file is:

```text
results/retrieval_examples/human_evaluation.csv
```

It contains:

- 10 query captions
- 3 retrieved clips for each caption
- 5 listener IDs
- 150 total rating rows

The five group members use listener IDs `1`, `2`, `3`, `4`, and `5`. Each member should complete the 30 rows assigned to their listener ID.

For each row:

1. Read the `query_caption`.
2. Identify the retrieved audio using `retrieved_audio_id`.
3. Listen to the retrieved clip.
4. Compare what is heard with the caption.
5. Enter a number from 1 to 5 in `rating_1_to_5`.
6. Optionally write a short reason in `notes`.

Do not change these fields:

- `query_audio_id`
- `query_caption`
- `retrieved_rank`
- `retrieved_audio_id`

Only the rating and optional notes should be added.

## 8. Does the rating update the caption or the model?

No. The caption is fixed source data from MusicCaps. We do not rewrite or update the caption based on a listener rating.

The human rating also does not currently retrain the model. It is evaluation evidence collected after retrieval. It tells us how convincing the model's retrieved results are to people.

The relationship is:

```text
Caption -> model embedding -> similarity ranking
Caption + retrieved audio -> human judgment -> rating
```

The similarity creates the ranking. The human rating evaluates that ranking. They are two separate measurements.

## 9. Aggregating the ratings

After all five group members complete their rows, run:

```powershell
python src/aggregate_human_evaluation.py `
  --input results/retrieval_examples/human_evaluation.csv `
  --output results/retrieval_examples/human_evaluation_summary.json
```

The summary reports:

- expected ratings
- completed ratings
- missing or invalid ratings
- overall mean score
- score distribution
- mean score by retrieval rank
- completion status

A complete evaluation should contain 150 valid ratings, with no missing or invalid values.

## 10. Final Task 4 interpretation

Task 4 has three evidence layers:

1. **Training:** the GNN and DistilBERT learn a shared audio-caption space.
2. **Automatic retrieval:** Recall@1, Recall@5, and Recall@10 measure whether known matching items are retrieved.
3. **Human evaluation:** five listeners judge whether the retrieved audio genuinely matches the caption.

The automatic metrics show how the model ranks paired items. The human ratings show whether those rankings make sense to people. Both are useful, but neither replaces the other.
